# Supabase local tooling

This directory is now a proper Supabase CLI project (`supabase/config.toml`,
generated by `supabase init`). Nothing about the migration chain changed —
`config.toml` just tells the CLI where things already live:

- `migrations/` — the tracked, ordered migration chain (unchanged).
- `seed.sql` — local/dev-only demo data, applied by `db reset` after
  migrations (see the file's own header comment). Never applied by
  `db push` or to production.
- `schema.sql` — a **reference snapshot of the live project's public schema**
  (tables, columns, constraints, indexes, RLS, policies), regenerated from the
  live database on 2026-09-18. It is documentation of what exists, **not** a
  bootstrap script: the migrations already ran against the live project, so
  replaying them on top of a database created from this file fails on objects
  that already exist. Functions, views, triggers and grants are not in it (its
  header lists them); their bodies live in `migrations/`. Regenerate it after a
  migration changes structure instead of hand-editing.

  The old version of this file was a hand-written starter script that had
  drifted far from the live schema (tables that don't exist live, missing
  columns, ~20 missing tables). Standing up a brand-new project from scratch
  is therefore not currently a supported path — that is still open under issue
  #34.

## Local workflow (once Docker is available)

```sh
# one-time: install the CLI (see https://supabase.com/docs/guides/local-development/cli/getting-started)
supabase start          # boots local Postgres + Studio + Auth via Docker
supabase migration list   # compares local vs. remote applied migrations
supabase db diff -f <name> # generate a new migration from a schema change
```

`supabase start` requires Docker with outbound network access to pull the
Supabase service images. This repo's CI/sandbox environments may not have
that (Docker daemon present but image pulls blocked, or no Docker at all).
`supabase db reset` replays `migrations/` + `seed.sql` onto an empty
database; since the baseline migration (issue #276) and the
`item_categories` replay guard added for issue #278, that from-scratch
replay works.

## Database tests (pgTAP)

`tests/*.sql` are pgTAP tests for the RLS policies and SECURITY DEFINER RPCs
(issue #278): tenant isolation, anon access, the `place_*_order` RPCs,
merchant catalog writes / order transitions, and the admin/account RPCs.
Each file runs in one transaction that is rolled back, so it leaves no data
behind.

```sh
supabase db start
supabase db reset   # optional: fresh replay of migrations + seed
supabase test db
```

The `Supabase CI` workflow (`.github/workflows/supabase.yml`, job `db-test`)
runs exactly these commands on every PR that touches `supabase/**`.

## Linking to the live project (manual, human-only)

`supabase link` / `supabase db pull` against the real project requires live
project credentials and is **never** run by the automated board worker —
see issue #34 for the tracked follow-up (recovering table DDL, e.g.
`restaurant_locations`, that exists live but was never captured as a
migration). Do this yourself, locally, with your own Supabase access token.
