# Multi-Agent Setup

Full source of truth is always `.claude/agents/*.md` and `.claude/skills/build/SKILL.md` (both live in this repo, at `chowflow_flutter/.claude/`) — this note is a map/summary, not a copy. Read the actual files before dispatching if the details matter; they're short.

## The four subagents

- **`ui-agent`** — visual/presentation. `lib/screens/`, `lib/widgets/`, `lib/config/theme.dart`+`tailwind.dart`, plus `*_screen.dart`/`*_page.dart`/`presentation/widgets/*` files inside any domain's `presentation/` folder. Model: sonnet.
- **`logic-agent`** — app wiring, state, business logic. `lib/app/`, `lib/main.dart`, cross-cutting `lib/platform/{session,system_ui,localization}/`, plus every domain's `data/`/`models/` folders and any `*_controller.dart`/`*_service.dart`/`*_repository.dart` file even when colocated inside `presentation/`. Model: sonnet.
- **`supabase-agent`** — `supabase/` only (migrations, schema, RLS, edge functions). Model: **opus** (higher stakes — schema/RLS mistakes are the costliest to get wrong).
- **`qa-agent`** — `test/` only, runs after the others (not alongside), since it needs to read the finished diff. Model: sonnet.

**Unowned by design**: `pubspec.yaml`, `pubspec.lock`, and native platform shells (`android/`, `ios/`, `macos/`, `linux/`, `windows/`, `web/`) belong to none of the four — added 2026-08-13 after finding these had no owner at all. The orchestrator (whoever's running `/build`) handles these directly rather than dispatching, since they're high-conflict/high-stakes (dependency changes, native manifests) and no subagent's prompt covers them.

**Creating a brand-new top-level project (e.g. a second Flutter app in the repo) is the same kind of orchestrator-owned work, not a human-only task.** This got misread once (issue #132, 2026-08-30 — see [[Decisions Log]]/[[Open Tasks]] 2026-09-15 for the reversal): a run reasoned "no subagent owns creating a new app" and escalated to `waiting-on-you`, and the owner initially agreed in writing. That framing was too conservative and was explicitly walked back 2026-09-15 — the orchestrator creating a new `flutter create`-style project directory is no different in kind from it editing `pubspec.yaml` directly, both already established as orchestrator-owned. Once an issue's actual open product/scope questions are answered (repo structure, naming, etc.), treat "this needs a whole new project" as implementation detail, not a reason to defer to a human.

**Critical gotcha already hit once**: the scope definitions were originally written against a flat `lib/screens/`+`lib/widgets/` view of the codebase. The real layout moved to domain-based `features/services/platform` with controllers colocated inside `presentation/` folders (see [[Architecture]]). Both `ui-agent` and `logic-agent` correctly *refused* to touch out-of-scope files rather than guessing — which is the system working as intended, not a failure. If dispatching an agent and it refuses on a file that seems like it should obviously be in scope, the scope definition is probably stale again — check the actual current directory structure and fix `.claude/agents/*.md` before re-dispatching, don't just force it.

**Model override**: a `model:opus` or `model:sonnet` label on the driving GitHub issue overrides every agent's default model for that task.

**Nesting limit found 2026-08-27 (9th board-worker run)**: when the board worker dispatches one top-level agent per GitHub issue via its own `Agent` tool call (current practice, see step 4 below), that dispatched agent does **not** itself have an `Agent`/`Task` tool available to further fan out to `ui-agent`/`logic-agent`/`supabase-agent`/`qa-agent` — nesting only goes one level deep. All 6 agents in that run independently hit this and implemented directly instead, staying inside the relevant role's declared file scope by hand (not a failure — the file-scope discipline held even without the actual subagent dispatch). This means in practice the current board-worker/`/build` combination collapses to **one agent doing everything for a given issue**, not real parallel role-agents, whenever the top-level dispatch is itself already inside an `Agent` call. If genuine parallel role-agent dispatch matters for a specific issue (e.g. a large cross-cutting change), the board worker's own top-level session — not the per-issue dispatched agent — is the one that needs to make the `ui-agent`/`logic-agent`/etc. `Agent` calls directly, before/instead of wrapping the whole issue in a single outer agent.

**Flutter SDK is not guaranteed to be pre-installed in a session's container, found 2026-09-13 (66th board-worker run)**: this run's container had no `flutter`/`dart` on `PATH` or anywhere on disk at all — every prior status-log entry that quotes real `dart format`/`flutter analyze`/`flutter test` output implies those sessions' containers *did* have it, so availability apparently varies per container rather than being a fixed guarantee. When missing, a dispatched worktree-isolated agent cannot run the DoD checks either (confirmed: an issue #3 sub-agent independently hit the same "SDK not found" and had to skip verification). Fixed for future sessions by adding `.claude/hooks/session-start.sh` + `.claude/settings.json` (a `SessionStart` hook that auto-installs Flutter to `/opt/flutter` and symlinks it into `/usr/local/bin`, idempotent) — merged as PR #188. Also fixed `.tool-versions` itself: it pinned `flutter 3.41.9`, which cannot actually run `flutter pub get` on this project (`flutter_native_splash ^2.4.8` needs `meta ^1.18.0`, which 3.41.9's bundled `flutter_test` doesn't provide) — bumped to `3.47.4`. **If a future run finds Flutter missing again**: check first whether `.claude/settings.json` and the hook script are actually present in the checkout (a session that started before this PR merged, or a checkout that somehow lost `.claude/`, would still need the old manual fallback: download `https://storage.googleapis.com/flutter_infra_release/releases/stable/linux/flutter_linux_<version>-stable.tar.xz` matching `.tool-versions`, extract to `/opt/flutter`, symlink `flutter`/`dart` into `/usr/local/bin` since non-interactive `bash -c` shells don't source `~/.bashrc`/`/etc/profile`).

**A `todo`+`agent-in-progress` issue with no branch, no PR, and no vault trace of work is a stale label, not real in-progress work, found 2026-09-14 (67th board-worker run)**: run start found #34 and #40 both carrying `agent-in-progress` from some earlier point, but `list_branches`/`list_pull_requests` showed no `agent/issue-34-*`/`agent/issue-40-*` branch or PR ever existed, and the vault's own Status Log/Open Tasks had both listed as "next up, not yet picked" as of the prior run — i.e. the label was set (by an unknown prior run or a manual slip) without any actual work following it. Treated as a labeling artifact and picked both up normally rather than skipping them forever (a strict "never touch `agent-in-progress`" reading would have permanently orphaned them, since nothing else would ever clear the label). If a future run finds this again: check `list_branches`/`list_pull_requests` for the issue's expected `agent/issue-<n>-*` branch name and check this vault for any note of an actual attempt before deciding it's stale versus genuinely (if oddly) mid-flight in a run that hasn't finished yet.

**GitHub MCP tool access is inconsistent across dispatched agent sandboxes, found 2026-08-30 (14th board-worker run)**: `supabase-agent` dispatches (#129/#130/#131/#136 that run) all had working `mcp__github__*` tools and successfully opened + squash-merged their own PRs end-to-end. `ui-agent` dispatches (#123/#137 the same run) did **not** — no `mcp__github__*` tools, no working `gh` CLI, `curl` to the API blocked — both correctly pushed their branch and stopped rather than guessing a workaround, and the orchestrator finished PR creation/merge on their behalf afterward. Cause not yet diagnosed (a difference between `supabase-agent`'s and `ui-agent`'s tool grants in `.claude/agents/*.md`? something about how each is invoked?) — until this is root-caused, assume a `ui-agent`/`logic-agent`/`qa-agent` dispatch may need the orchestrator to finish PR creation/merge itself (check its final report for "no GitHub MCP access" before assuming a PR already exists), while `supabase-agent` dispatches usually self-serve the whole flow. Worth a quick diagnostic pass on `.claude/agents/*.md` if this keeps recurring.

**When `mcp__github__*` tools are missing, `$GITHUB_TOKEN` + the plain REST API works as a fallback, confirmed 2026-09-14 (71st board-worker run)**: issue #31's `supabase-agent` dispatch had no GitHub MCP tools and no `gh` CLI, but `$GITHUB_TOKEN` was already present in its environment and plain `curl` calls against the GitHub REST API (through the proxy) successfully created and squash-merged its PR end-to-end. Tell a dispatched agent to try this before falling back to "push the branch and stop" — it may be able to self-serve the whole flow after all.

**A dispatched agent can end its own turn mid-CI-wait expecting a notification it doesn't have, found 2026-09-14 (71st board-worker run)**: two agents (#37, #42) opened a PR, saw the CI check still `in_progress`, and ended their turn saying they'd "wait for the CI monitor" — but a leaf subagent dispatched via `Agent` has no standing background-notification channel of its own; each resumption just re-checked and reported "still waiting," doing nothing to actually advance. The orchestrator had to poll `GET /repos/{owner}/{repo}/commits/{sha}/check-runs` itself (the `Monitor` tool with a `curl`+`$GITHUB_TOKEN` poll loop worked well) and was prepared to finish the merge itself once green — in #42's case the agent's own eventual resumption happened to land the merge first, in #37's case it explicitly polled in-loop within one turn per an updated prompt and finished cleanly. **Fix applied**: dispatch prompts now explicitly instruct the agent to poll check-run status itself in a `sleep`-loop *within a single tool call*, rather than ending its turn while CI is still running — do this for any future dispatch that self-merges after CI.

**This sandbox's outbound proxy allowlist is asset-type-specific, not a blanket allow/deny, found 2026-09-15 (72nd board-worker run)**: while working issue #44 (bundle real onboarding imagery) and #45 (bundle a real font) in the same run, `lh3.googleusercontent.com` (a Google Stitch design-tool image host) got `CONNECT tunnel failed, response 403` from the proxy, while `fonts.gstatic.com`/`fonts.googleapis.com` (Google Fonts) were fully reachable and let an agent download real `.ttf` files. Issue #46's agent separately found Google's Maven/AGP repo also blocked (`gradle -p android help` failed resolving the Android Gradle Plugin), and there's no Android SDK in this environment at all, so a real `flutter build apk/appbundle --release` can't be run here either. **Takeaway**: don't assume "network blocked" or "network fine" from one host — check the actual host you need per-issue (`curl -sS -o /dev/null -w '%{http_code}\n' <url>`) before deciding whether a fetch-dependent task is feasible or needs to be scoped down/flagged as a follow-up.

## `/build` skill

`.claude/skills/build/SKILL.md`. Given a feature request: (1) read the code, (2) ask clarifying questions only if genuinely ambiguous, **capped at 3 per round** — interactively via `AskUserQuestion`, or async (see below) if no live user, (3) rewrite into a fixed-shape task brief (goal, in/out-of-scope, constraints/assumptions, acceptance criteria, verification commands — not free-form prose), (4) decide which agents are actually needed, (5) define shared contracts (method signatures, table/RPC names, routes) *before* dispatching so parallel agents' work fits together without talking to each other, (6) dispatch the needed agents in parallel (single message, multiple `Agent` calls), (7) reconcile + `flutter analyze`, (8) optionally dispatch `qa-agent`, (9) summarize, (10) update the vault (mandatory, see step 10 in the actual file for exactly what's required vs. conditional).

**When dispatching read-only investigation agents (audits, not `/build` feature work)**: point them at `vault/00-Index.md` explicitly in the prompt, not just the code. One investigation agent on 2026-08-13 wasn't told to read the vault, independently rediscovered the exact `chowflow_flutter/`-path confusion [[Conventions]] already warns about, and produced a wrong finding as a result (see [[Decisions Log]] 2026-08-13). Agents without the vault's context can waste effort rediscovering — and getting wrong — things already answered here.

## Scheduled board worker

A cron routine ("eatzy board worker", every 5 hours) runs in Anthropic's cloud, independent of any interactive session — see [[Conventions]] for the label protocol it follows. It:
0. **Never acts on `needs-approval`-labeled issues** — only `todo` (approved) or `waiting-on-you` (already-approved, paused on a question). Added 2026-08-13 as an explicit gate; see [[Conventions]] and [[Decisions Log]] 2026-08-13.
1. Checks `waiting-on-you`-labeled issues first — if the human replied to a previously-asked clarifying question, resumes that task.
2. Otherwise picks the oldest `todo`-labeled issue. If ambiguous, comments with specific questions and relabels `waiting-on-you` instead of guessing. If clear, claims it (`agent-in-progress`) and implements via the same `/build` flow.
3. Always opens a PR against `master`, never pushes directly, never merges itself.
4. **Processes up to 6 eligible issues per run** (added 2026-08-15), looping back to step 1 after finishing/pausing each one instead of stopping after the first. Each issue's actual implementation is dispatched via `Task` as its own fresh unit of work — no diffs/tool-output/discussion detail carried from a previously finished issue into the next one's context, only lightweight bookkeeping (issue number, count so far) persists across loop iterations. This keeps the top-level routine session cheap regardless of how many issues it works in a cycle, and keeps unrelated issues from bleeding into each other, without needing a separate cloud session per issue (the routine API only spawns one session per cron fire).
5. **This vault is committed inside the repo specifically so the board worker can read it too** — if updating the routine prompt, point it at `vault/00-Index.md` first so it doesn't re-explore the whole codebase cold every run.

## Parallelism policy

Within one task spanning layers, dispatch relevant agents in parallel (that's the whole point of the role split). Across *different* tasks: parallelize only when they touch genuinely disjoint files (e.g. a `lib/services/` refactor + a `supabase/` doc fix ran together safely); default to one-at-a-time when tasks might overlap or build on each other.
